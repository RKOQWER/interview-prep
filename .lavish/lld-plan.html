Low-Level Design, code-first

You learn the small slice of TypeScript that carries LLD interviews, the OOP / SOLID / pattern vocabulary interviewers score, one repeatable method for turning a problem statement into classes, then 14 classic problems coded and tested end to end. TypeScript is the working language; Python is used only to compare how a design reads in your everyday language. One of three separate plans. Minimum 1 hour per day.

How every session runs

Same loop every time. You write the majority of the code.

1

Recall

5 min. Rebuild last session's pattern or class design from memory, no notes.

2

Concept

One idea, one reason it matters, one tiny example. Never a wall of theory.

3

Violation to fix

A bad code smell, then the fix. This is the format shown below.

4

Build

You code the exercise or problem in lld/. I review, we fix, we discuss trade-offs.

5

Wrap

2 min. Tests green, one commit, one trade-off sentence for the log.

Mastery gate (your rule): if a concept feels even slightly shaky, we do not move on. I add more problems on that exact concept until you can explain it and code it cold.

Sequence: M0-M3 in October, patterns and Tier 1-2 problems in November, Tier 3 and interview craft in December.

The modules

M0

The workbench

1 session
  • Scaffold inside lld/: Node + TypeScript in strict mode + tsx to run files + vitest for tests
  • Conventions: one class per file, interfaces separated from implementations, tests next to code

You'll code: the setup itself, then take a deliberately failing test and make it pass.

M1

The TypeScript survival kit

7 sessions
  • Types, inference, function signatures, unions, literal types, recording behavior with types
  • Null safety: strict mode, optional chaining, nullish coalescing
  • Objects: interface vs type, optional and readonly properties, structural typing (the big mind-shift)
  • Classes deep dive: constructors, parameter properties, access modifiers, getters/setters, static, abstract vs interface
  • Generics, just enough: containers like Repository<T>, constraints, and when NOT to genericize
  • Modules and file layout: imports, circular imports, enums vs literal unions
  • Errors: custom error classes, fail-fast design

You'll code: a typed Task Manager mini-app, 10-12 small files, no design patterns yet. Every concept gets its Python analogue first, then the differences.

M2

OOP that gets scored

2 sessions
  • Encapsulation means invariants, not getter/setter boilerplate
  • Abstraction: callers depend on the interface, not the implementation
  • Inheritance vs composition: the is-a / has-a test, and why composition is the default
  • Polymorphism: killing if/else chains on object type
  • Abstract class vs interface decision rule: shared state goes to an abstract class, everything else to an interface

Drills: refactor a procedural script into objects; replace a type-switch with polymorphism.

M3

SOLID in code

2 sessions
  • One principle at a time, always as violation - fix - your drill
  • S: split classes by change driver, not by size
  • O: add a new payment type without editing existing code
  • L: repair a broken hierarchy (the Square/Rectangle trap)
  • I: split fat interfaces (the throws-UnsupportedOperation test)
  • D: inject interfaces instead of constructing dependencies, and why that makes tests trivial

Proof mechanic: every fix must make a failing test pass and keep every other test green.

M4

Pattern toolbox

5 sessions
  • Creational: Factory Method, Builder, Singleton vs registry (and why dependency injection usually beats Singleton)
  • Behavioral: Strategy, State, Observer, Command, Template Method, Chain of Responsibility
  • Structural: Adapter, Decorator, Facade, Proxy, Composite
  • Each pattern: the signal in a requirement that should trigger it, the skeleton, one mini build
  • Confusion pairs interviewers love: Strategy vs State, Decorator vs Proxy, Adapter vs Facade
  • Anti-pattern radar: God class, premature abstraction, pattern soup

You'll code: a small build per pattern, then the same pattern applied inside a real problem.

M5

The method: problem statement to classes

2 sessions

Your stated weak spot, so it gets its own framework. The 8 steps:

  1. Clarify: functional requirements, constraints, what is out of scope
  2. Underline nouns - candidate entities
  3. Underline verbs - behaviors and responsibilities
  4. Write invariants: what must always be true per entity
  5. Find variation points - interfaces go here, and only here
  6. Map relationships: has-a, is-a, uses-a
  7. Trace 2-3 workflows end to end, happy path then edge cases
  8. Name the public API before writing any implementation

Format: I model 2 problems end to end, thinking aloud. Then you co-drive one: you sketch, I review, we refine. Every design ends as interfaces + class shells, then code.

M6

Problem lab - the core of the track

9-10 sessions

Each problem runs the same loop: interviewer-style prompt - you clarify - you sketch the skeleton - we code it - tests - then the twist ("now add X"). Patterns are never the goal, they are the outcome.

The curated TypeScript subset

You said you do not want to learn all the functions. Agreed. This is the whole list we drill, always inside a real problem. Where a function mirrors a Python structure you already know (dict, set, list operations), we call out the equivalence so it sticks faster.

CategoryThe functions we drillWhy they carry your code
Arrays map filter reduce find findIndex some every flatMap includes sort slice spread Turn collections inside out without mutable index loops. Also: the sort mutation trap.
Map and Set Map for registries and caches, Set for uniqueness and dedup, get/set/has/delete/values The two data structures behind half of all LLD solutions. Prefer Map over plain objects for lookups.
Objects Object.keys Object.values Object.entries Object.fromEntries spread Object.freeze Configs, registries, safe copies, protecting invariants.
Strings split join includes startsWith endsWith replace replaceAll padStart + template literals Parsing commands, formatting receipts and log lines.
Control flow for...of, iteration order, when forEach is wrong, when map is wrong Straight-line readable code instead of index bookkeeping.

Everything else (regex deep-dives, currying, exotic array methods) is added only if a real problem demands it.

A taste of the teaching style

Every lesson is a smell, then a fix. Here is the exact move you will learn in M3 and reuse in the Parking Lot problem.

Before: if/else on type - a hidden open/closed violation. Every new vehicle type edits this class.

After: one interface, one class per rate. New type = new class, zero edits here.

The real-world thread

Production note per session

Two minutes at the end: where this pattern lives in production code. Strategy in a pricing service, State in order workflows, Observer in event systems.

Weekly application task

Once a week, apply or refactor one thing in your real work repo. Five lines in lld/notes.md: what changed, why it is better, the trade-off.

Trade-off log

Every design decision gets one sentence: chose X over Y because of requirement Z; the cost is C, acceptable because D. Same sentence shape as interviews and PR discussions.
