Every concept ends with how it shows up in real production code, so the preparation compounds at work too.

The daily triad

One focused block per day, all three tracks inside it. 60 minutes minimum, 90 when the day allows, with weekends for deeper builds. The design slot alternates LLD and HLD days; DSA runs every day.

25-40 min. Alternates days: LLD (write TypeScript with tests) and HLD (requirements, estimation, diagram, trade-offs).

5 min. Three-line log: what I learned, what is shaky, tomorrow's focus. Everything goes in your repo.

Mastery gate (your rule, locked in): if a concept feels even slightly shaky, we do not move on. I add more problems on that exact concept, in any track, until you can explain it and use it cold.
Weekends: one longer build (a full LLD problem coded to green tests, or a complete HLD walkthrough) plus one timed DSA set. This is where depth accumulates.

The three tracks

Track D

Data Structures and Algorithms

What senior rounds test: pattern recognition under time pressure, complexity reasoning, clean code and clear thinking out loud.

How we train it: pattern families instead of random problem roulette. 1-2 problems daily, one timed set weekly, every solution reviewed and logged in three lines: the signal, the complexity, the mistake to avoid. Working language: Python.

Track L

Low-Level Design

What senior rounds test: turning requirements into classes with clear responsibilities, SOLID, patterns only where the requirement demands them, working TypeScript.

How we train it: the module course below (M0-M7) plus 14 classic problems coded end to end with tests and interviewer twists. TypeScript is the primary language; the occasional Python port is used only to compare.

Track H

High-Level Design

What senior rounds test: requirements and scope, back-of-envelope estimation, component architecture, deep dives, trade-offs and failure modes.

How we train it: 12 classic systems, diagram-first, always ending with bottlenecks and trade-offs. We use Mermaid diagrams you can re-draw in an interview.

Track L - Low-Level Design (TypeScript)

Code-first, as you asked. M0-M3 run in October, patterns and Tier 1-2 problems in November, Tier 3 and interview craft in December. Every module is mostly you writing code.

M0

The workbench

1 session
  • Three folders, already created in interview-prep: dsa/, lld/, hld/ - tracked completely separately
  • lld/: Node + TypeScript in strict mode + tsx to run files + vitest for tests. dsa/: plain Python, runnable with python3. hld/: design notes + Mermaid diagrams
  • Conventions: one class per file, interfaces separated from implementations, tests next to code (LLD); one file per pattern with your three-line notebook note (DSA)

You'll code: the repo itself, then take a deliberately failing test and make it pass.

M1

The TypeScript survival kit

7 sessions
  • Types, inference, function signatures, unions, literal types, recording behavior with types
  • Null safety: strict mode, optional chaining, nullish coalescing
  • Objects: interface vs type, optional and readonly properties, structural typing (the big mind-shift)
  • Classes deep dive: constructors, parameter properties, access modifiers, getters/setters, static, abstract vs interface
  • Generics, just enough: containers like Repository<T>, constraints, and when NOT to genericize
  • Modules and file layout: imports, circular imports, enums vs literal unions
  • Errors: custom error classes, fail-fast design

You'll code: a typed Task Manager mini-app, 10-12 small files, no design patterns yet.

The curated stdlib subset is drilled across this module - see the list further down.

M2

OOP that gets scored

2 sessions
  • Encapsulation means invariants, not getter/setter boilerplate
  • Abstraction: callers depend on the interface, not the implementation
  • Inheritance vs composition: the is-a / has-a test, and why composition is the default
  • Polymorphism: killing if/else chains on object type
  • Abstract class vs interface decision rule: shared state goes to an abstract class, everything else to an interface

Drills: refactor a procedural script into objects; replace a type-switch with polymorphism.

M3

SOLID in code

2 sessions
  • One principle at a time, always as violation - fix - your drill
  • S: split classes by change driver, not by size
  • O: add a new payment type without editing existing code
  • L: repair a broken hierarchy (the Square/Rectangle trap)
  • I: split fat interfaces (the throws-UnsupportedOperation test)
  • D: inject interfaces instead of constructing dependencies, and why that makes tests trivial

Proof mechanic: every fix must make a failing test pass and keep every other test green.

M4

Pattern toolbox

5 sessions
  • Creational: Factory Method, Builder, Singleton vs registry (and why dependency injection usually beats Singleton)
  • Behavioral: Strategy, State, Observer, Command, Template Method, Chain of Responsibility
  • Structural: Adapter, Decorator, Facade, Proxy, Composite
  • Each pattern: the signal in a requirement that should trigger it, the skeleton, one mini build
  • Confusion pairs interviewers love: Strategy vs State, Decorator vs Proxy, Adapter vs Facade
  • Anti-pattern radar: God class, premature abstraction, pattern soup

You'll code: a small build per pattern, then the same pattern applied inside a real problem.

M5

The method: problem statement to classes

2 sessions

Your stated weak spot, so it gets its own framework. The 8 steps:

  1. Clarify: functional requirements, constraints, what is out of scope
  2. Underline nouns - candidate entities
  3. Underline verbs - behaviors and responsibilities
  4. Write invariants: what must always be true per entity
  5. Find variation points - interfaces go here, and only here
  6. Map relationships: has-a, is-a, uses-a
  7. Trace 2-3 workflows end to end, happy path then edge cases
  8. Name the public API before writing any implementation

Format: I model 2 problems end to end, thinking aloud. Then you co-drive one: you sketch, I review, we refine. Every design ends as interfaces + class shells, then code.

M6

Problem lab - the core of the track

9-10 sessions

Each problem runs the same loop: interviewer-style prompt - you clarify - you sketch the skeleton - we code it - tests - then the twist ("now add X"). Patterns are never the goal, they are the outcome.

Diagram-first. Every system gets the same 7-part treatment, and every design ends with bottlenecks, trade-offs, and failure modes, which is exactly what senior rounds score. We generate Mermaid diagrams, and you learn to reproduce them on a whiteboard in under 10 minutes.

The 7-part treatment for every system

  1. Functional and non-functional requirements, and what is explicitly out of scope
  2. Back-of-envelope estimation (QPS, storage, bandwidth)
  3. API design
  4. Data model and storage choices
  5. High-level diagram (Mermaid: clients, services, queues, caches, stores)
  6. Deep dive on the two hardest bottlenecks
  7. Trade-offs, failure modes, and what you would change at 10x scale

The real-world thread

You asked to apply all of this at work, not just pass interviews. Every track has a thread that connects concepts back to your actual codebase.

Production note per session

Two minutes at the end of each session: where this concept lives in production. Strategy in a pricing service, State in order workflows, sharding in a database you have used, caching where you have seen it fail.

Weekly application task

Once a week, pick one concept and apply or refactor something in your real work repo. Five lines in the notes folder: what changed, why it is better, what the trade-off was.

Trade-off log

Every design decision gets one sentence: chose X over Y because of requirement Z; the cost is C, acceptable because D. That exact sentence shape works in interviews and in PR discussions.

A taste of the teaching style (Track L)

Every lesson is a smell, then a fix. Here is the exact move you will learn in M3 and reuse in the Parking Lot problem.

Before: if/else on type - a hidden open/closed violation. Every new vehicle type edits this class.

After: one interface, one class per rate. New type = new class, zero edits here.
