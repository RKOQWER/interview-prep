# M1 - The TypeScript Survival Kit (7 sessions)

We build toward one artifact: a typed Task Manager mini-app (10-12 small files, no patterns yet). Every concept lands as code in that app. Python analogue called out each time so it hooks to what you already know.

## Session 1 - Types, inference, signatures, unions, literal types

**Recall (M0):** why `strict: true` is on. `strictNullChecks` is the one that most changes how you write code - a value that can be missing must be checked before use.

**Concept:** TypeScript's job is to make illegal states unrepresentable *at compile time*. Three tools today:

1. Inference - you usually don't annotate locals. `const n = 5` is already typed `number`. Annotate at boundaries (function params/returns, public APIs).
2. Union types - a value that can be one of several things: `string | number`.
3. Literal types + unions of literals - the closest thing to Python's enums for cheap: `"todo" | "in_progress" | "done"`.

Python analogue: `Literal["todo", "in_progress", "done"]` from `typing`, and `Union[str, int]`.

```ts
type Status = "todo" | "in_progress" | "done";

function labelFor(status: Status): string {
  switch (status) {
    case "todo": return "Not started";
    case "in_progress": return "Working on it";
    case "done": return "Finished";
  }
}
```

Why no `default` in that switch: when the input is a union type, TS proves every case returns a string. Add a 4th status (`"archived"`) to the union and this switch errors with "Not all code paths return a value" - forcing you to handle it. The compiler is your exhaustiveness checker.

If you add `default: return "out of syllabus"` instead, the exhaustiveness protection disappears: a new status silently falls into `default`, no error, wrong behavior ships. Rule: for union-typed switches, omit `default` so TS can check completeness. Use `default` only for open-ended types like `string`.

**Function signatures** - annotate params and return type at module boundaries:

```ts
function add(a: number, b: number): number { return a + b; }
```

Inside small closures/callbacks, inference is fine.

**Task Manager step 1.** Create `lld/src/task.ts`:

```ts
export type Status = "todo" | "in_progress" | "done";

export interface Task {
  id: number;
  title: string;
  status: Status;
}
```

And `lld/tests/task.test.ts` with a couple of assertions around a small pure function you write, e.g. `moveTask(task, status): Task` (returns a NEW task object - do not mutate).

```ts
it("moves a task without mutating the original", () => {
  const t: Task = { id: 1, title: "Write tests", status: "todo" };
  const t2 = moveTask(t, "done");
  expect(t2.status).toBe("done");
  expect(t.status).toBe("todo"); // original untouched
});
```

Hint for immutability: `{ ...t, status }` (spread makes a shallow copy).

**Definition of done:** `npx vitest run` green, `npx tsc --noEmit` clean, no `any` anywhere.

**Wrap:** commit `M1.1: task types + union status`, one trade-off sentence (e.g. "chose literal union over a string + comments because the compiler then rejects typos; cost is no runtime validation of external data - handled later at boundaries").

## Session 1 discussion notes - type vs interface vs abstract class

The decision rule (memorize):

```
Need a contract only?                          -> interface
Need a name for a union/primitive/shape?       -> type
Need to share STATE or IMPLEMENTATION too?     -> abstract class
Just one concrete thing, no variation?         -> plain class, no interface yet
```

Level-by-level example the rule came from (Task Manager storage):

- Level 0: plain `TaskStore` class. Problem: you may later swap in Postgres, and tests need fakes. Callers must not depend on the concrete class.
- Level 1: `interface TaskRepository { save(t); findById(id); }` - callers depend on the abstraction (DIP). New implementations don't edit callers (OCP).
- Level 2: `type Status = "todo" | "in_progress" | "done"` - `type` for unions/computed shapes; `interface` for object contracts only.
- Level 3: `abstract class BaseTaskRepo implements TaskRepository` - only when subclasses share state or implementation (e.g. common `validate` + `logger` before `save`). If nothing is shared, it's overkill.

Interview reflex: interface at every variation point (storage, pricing, notification). No interface where there is no variation point.

## Session 1 discussion notes - aliasing, shallow vs deep copy

- **Aliasing**: `const b = a` - two names, same object. Mutate via `b`, `a` changes too.
- **Shallow copy**: `{ ...a }` / `Object.assign` / `arr.slice()` - new top-level object, nested objects/arrays are STILL aliased. Mutating a nested array through the copy leaks into the original.
- **Deep copy**: `structuredClone(a)` - recursively new everything. `JSON.parse(JSON.stringify(a))` is the legacy hack (breaks on Date, Map, functions).

Why it matters for `moveTask(t, status)`: `{ ...t, status }` gives a new Task with a new `status` - original `t` stays put. But if `Task` later has a nested object (`createdBy: User`), the nested object is still shared; don't mutate it through the copy.

Python analogue: `b = a` (alias), `b = dict(a)` (shallow), `copy.deepcopy(a)` (deep). Same semantics.

## Session 2 - Null safety: strict mode, optional chaining, nullish coalescing

**Concept:** With `strictNullChecks` on, `undefined`/`null` are part of the type. The compiler stops you from dereferencing something that might be missing. The trio that handles it:

- `?.` optional chaining - short-circuits to `undefined` if the left side is nullish.
- `??` nullish coalescing - fallback ONLY when left is `null | undefined`.
- `||` - fallback on ALL falsy (use only when every falsy means "missing").

```ts
function assigneeName(t: Task): string {
  return t.assignee?.name ?? "unassigned";
}
```

`t.assignee` is `User | undefined` -> `?.name` yields `string | undefined` -> `??` fixes the fallback. Each step is typed, no hidden nulls.

Python analogue: `getattr`-style defensive chains replaced by explicit types.

**Build:** extend `Task` with optional `assignee?: { name: string }` and write `assigneeName`. Tests: assigned task returns name; unassigned returns `"unassigned"`; task with empty-string name stays `""` (why `??` not `||`).

**Definition of done:** vitest green, `tsc --noEmit` clean, and you can explain why `"" ?? "x"` keeps `""` while `"" || "x"` doesn't.

**Wrap:** commit `M1.2: null-safe assignee`.

Feedback on session 1 code: annotate the return type at the boundary (`moveTask(t: Task, s: Status): Task`), and pick one spelling for the status literal - `"in_progress"` is safer than `"in progress"` in keys/URLs/enums.

## Session 3 - Objects: interface vs type, optional/readonly, structural typing

**Concept:** TypeScript types are STRUCTURAL, not nominal. Two types are compatible if their shapes match, even if declared independently:

```ts
interface Task { id: number; title: string; status: Status; }
const t1: Task = { id: 1, title: "x", status: "todo" };
const t2: Task = { id: 2, title: "y", status: "done", extra: 1 }; // ERROR: excess property
const t3 = { id: 3, title: "z", status: "todo" as Status, extra: 1 };
const t4: Task = t3; // OK - shape is compatible, extra keys allowed at assignment from a variable
```

That's structural typing: `t4` compiles because `t3` has AT LEAST the required shape. (Fresh object literals get the excess-property check - a safety net against typos.)

**Optional vs readonly:**

```ts
interface Task {
  id: number;
  readonly title: string;      // can't reassign after creation
  status: Status;
  assignee?: { name: string }; // may be absent
}
```

Python analogue: `@dataclass(frozen=True)`-ish for readonly, `Optional[...]` for optional.

**interface vs type (practical rule):** both describe shapes; use `interface` when extending object contracts (`extends`), use `type` for unions/intersections/primitives. They're 95% interchangeable for plain object shapes.

**Build:** make `id` and `title` readonly in `Task`, mark a new optional `dueDate?: string`, write a test that a freshly created task satisfies invariants (e.g. title non-empty).

**Definition of done:** vitest green, `tsc --noEmit` clean, and you can state the structural-typing rule in one sentence: assignment is allowed when the value has AT LEAST the required shape.

**Wrap:** commit `M1.3: readonly/optional task shape`.

## Session 3 discussion notes - visibility defaults + why structural typing

- Interfaces: everything is public, `public` is not allowed as a modifier there - an interface IS the public contract. Classes: members default to public; write `private`/`protected` only to hide.
- Why `const t2: Task = t1` works when `t1` has an extra `extra` key: TypeScript uses structural typing - assignment is legal when the value has AT LEAST the required shape.
  - Soundness: usages of `Task` only touch known members; extras can't break them.
  - JS reality: third-party/API objects often have the right shape without shared declarations; nominal typing would force editing them.
  - Inconsistency to know: fresh literals get the excess-property check (typos like `titel:` error immediately), variables assigned later don't.
- Mnemonic: nominal languages ask "did you say you were one of these?"; TypeScript asks "do you have at least these members?"

## Session 4 - Classes deep dive

**Concept:** constructor + access modifiers + getters/setters + static + abstract vs interface.

```ts
class TaskStore {
  private tasks: Task[] = [];                    // invariant: tasks never mutated in place

  constructor(readonly owner: string) {}         // parameter property: declares AND assigns

  get size(): number { return this.tasks.length; }  // getter: looks like a property at call site
  add(t: Task): void { this.tasks = [...this.tasks, t]; }
  static createEmpty(): TaskStore { return new TaskStore("anon"); }  // factory-ish helper
}
```

- Access modifiers on fields: `private` (only this class), `protected` (this + subclasses), none (public default).
- **Parameter properties** (`constructor(readonly owner: string)`): shorthand for declaring the field AND assigning it. Equivalent explicit Java-style version is equally idiomatic:

```ts
class TaskStore {
  private readonly owner: string;
  constructor(owner: string) { this.owner = owner; }
}
```

Pick one style per class; house style wins in real code.
- Getters/setters: `get x()` reads like `store.size`, keeps logic hidden. Use sparingly - don't fake Java beans.
- `static`: belongs to the class, not instances. Good for small factories/helpers; in business logic it becomes global state (a smell - covered in M2 DP thinking).
- `private` is compile-time only, same as `readonly`. For runtime hiding use JS-native `#field`.
- Abstract class vs interface: share state/implementation -> abstract class; pure contract -> interface. (Rule from session 1.)

**Python analogue:** `__init__(self, owner)` + `_private`-by-convention, but no enforced private; `@property` getters similar.

**Build:** convert the Task Manager store into a small `TaskStore` class with `add`, `findById`, `size` getter, and a static `empty()` factory. Tests: add + findById returns the task, size goes 0->1, original task object not mutated.

**Definition of done:** vitest green, `tsc --noEmit` clean, no public mutable fields (all `private` or `readonly`).

**Wrap:** commit `M1.4: TaskStore class`.

## Session 4 discussion notes - static

`static` = belongs to the class, callable without an instance: `TaskStore.empty()`.
Factory = a method returning a ready-made instance; use static for these (no instance state needed).
Use it for construction with a STORY (validation, wiring, named variants like fromCsv/empty). For a trivial default, prefer a default parameter: `constructor(readonly owner: string = "anon")`. Two factories for one optional field is YAGNI.
Use it for pure factories/helpers/per-class registries. Avoid it for hidden global mutable state - untestable, violates DIP.
`Logger.getInstance()`-style singleton statics are the classic trap.
Python analogue: `@classmethod def empty(cls)`.

## Session 5 - Generics, just enough

**Concept:** a generic is a type with a parameter - reuse the SHAPE of code across types without `any`.

```ts
class Repository<T> {
  private items = new Map<number, T>();
  add(id: number, item: T): void { this.items.set(id, item); }
  findById(id: number): T | undefined { return this.items.get(id); }
  list(): T[] { return [...this.items.values()]; }
}

const tasks = new Repository<Task>();          // T = Task
const users = new Repository<{ name: string }>(); // T = inline shape
```

`T` is a placeholder; instantiating fixes it. No `any` casts inside - the compiler flows the type through.

**Constraints** with `extends` - require the placeholder to have at least some shape:

```ts
function firstByStatus<T extends { status: Status }>(items: T[], s: Status): T | undefined {
  return items.find(i => i.status === s);
}
```

**When NOT to genericize:** if you only ever store one concrete type, plain `class TaskRepository` is clearer. Genericize at reuse points, not preemptively - premature abstraction. (Same YAGNI rule as interfaces.)

**Python analogue:** `Generic[T]` / `TypeVar`, same idea, more ceremony.

**Build:** extract a `Repository<T>` from TaskStore's array logic and store Tasks in it. Keep TaskStore tests green; add one test using a DIFFERENT T (e.g. `Repository<number>`) to prove reuse.

**Definition of done:** vitest green, `tsc --noEmit` clean, zero `any`.

**Wrap:** commit `M1.5: generic Repository<T>`.

## Session 5 discussion notes - object vs Map

- Plain object: fixed-shape record/config; keys coerced to strings; iteration via `Object.keys`; can collide with `Object.prototype` keys.
- `Map<K, V>`: real kv collection; any key type; `.size`, `has/delete`, insertion-order iteration; no prototype pollution; must convert via `Array.from` to serialize.
- Rule: objects for SHAPE (Task, config), Maps for LOOKUP (index by id, cache, registry). TaskStore/Repository uses `Map<number, Task>` because ids arrive at runtime.
- Gotcha: JS objects ARE open at runtime (`obj.x = 1` works), but TS types them as a fixed shape unless they have an index signature (`Record<string, V>`). Map gives dynamic keys + full types without that friction.

## Session 6 - Modules and file layout, enums vs literal unions

**Concept:** ESM imports/exports, circular imports trap, `enum` vs literal union.

```ts
// task.ts
export interface Task { ... }
// repository.ts
import { Task } from "./task";
```

Rules: one class per file; export the public contract at the top level; import only what you use.

**Circular import trap:** if `a.ts` imports `b.ts` and `b.ts` imports `a.ts`, module init order gets weird and you see `undefined` or TDZ errors at runtime. Fix by introducing a third module both depend on (usually `types.ts`). If you feel the need for a cycle, the design is usually telling you DIP was missed.

**enum vs literal union:**

```ts
enum Status { Todo, InProgress, Done }       // runtime object + forward/reverse mappings
type Status = "todo" | "in_progress" | "done"; // erased at compile time, plain strings
```

Default to the literal union: debuggable (the value IS the string), serializes cleanly, no `enum` import needed. Enums are worth it when you need reverse mapping or exhaustive iteration over a fixed set. Most LLD problems: union wins.

**Build:** move `Status`/`Task` into `src/types.ts` (or keep in `task.ts`) and make sure NO import cycle exists; add a `console.log(JSON.stringify(status))` sanity check that a Status prints as its literal.

**Definition of done:** vitest green, `tsc --noEmit` clean, one `enum` replaced by a literal union somewhere, no cycles.

**Wrap:** commit `M1.6: module hygiene`.

## Session 7 - Errors: custom error classes, fail-fast design

**Concept:** distinguish expected outcomes from exceptional failures, and fail fast.

```ts
export class NotFoundError extends Error {
  constructor(readonly resource: string, readonly id: number) {
    super(`${resource} with id ${id} not found`);
    this.name = "NotFoundError";
  }
}

// fail-fast: invalid state is rejected at the boundary, not deep in the call stack
function createTask(id: number, title: string): Task {
  if (title.trim() === "") throw new Error("title must be non-empty");
  if (id <= 0) throw new Error("id must be positive");
  return { id, title, status: "todo" };
}
```

Rules:
- `Error` subclass for expected domain failures (NotFound, InvalidState) - callers can `instanceof` them.
- Plain `Error` (or typed class) for programmer errors / invalid construction - fail fast.
- Never swallow: `catch {}` or `catch (e) { /* ignore */ }` hides bugs. If you catch, handle or rethrow.
- Expected OUTCOMES that are common (like a task simply not being done) are return values, not errors. Exceptions are for the unhappy path.

Python analogue: `class NotFoundError(Exception)` - same idea.

**Build:** add `NotFoundError` to `types.ts` or its own file; make `Repository.findById` throw it via a new `mustFindById(id)` that composes on top; test the throw.

**Definition of done:** vitest green, `tsc --noEmit` clean, no empty catch blocks, at least one `instanceof` check in a test.

**Wrap:** commit `M1.7: custom errors + fail fast`.
