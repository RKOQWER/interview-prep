# M0 - The Workbench

Goal: a TypeScript workbench you can run and test in. By the end of M0 you have:
- strict-mode TypeScript
- `tsx` to run `.ts` files directly
- `vitest` for tests
- a red test that you turn green

## 0. Prereqs (check first)

```bash
node --version     # want v18+ (ideally v20+)
npm --version
```

## 1. Clean slate

`lld/package.json` is a bare `npm init` leftover. Its `test` script is a stub and `"type": "commonjs"` fights modern ESM style. Replace it with this:

```json
{
  "name": "lld",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "tsx watch",
    "test": "vitest run",
    "test:watch": "vitest",
    "typecheck": "tsc --noEmit"
  }
}
```

Why `"type": "module"`: matches how Node/TS ESM imports work (`import { x } from "./x.ts"`), avoids the commonjs/ESM interop trap.

## 2. Install dev deps

```bash
cd lld
npm install --save-dev typescript tsx vitest @types/node
```

What each one is:
- `typescript` - the compiler, gives you `tsc`
- `tsx` - runs `.ts` files without a build step (wraps esbuild)
- `vitest` - test runner; jest-compatible API, first-class ESM/TS
- `@types/node` - type definitions for `process`, `console`, etc.

## 3. tsconfig.json (strict mode is the point)

Create `lld/tsconfig.json`:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "types": ["node"],
    "noEmit": true
  },
  "include": ["src", "tests"]
}
```

What matters:
- `strict: true` - the big one. Enables `strictNullChecks`, `noImplicitAny`, etc. This is what makes TS worth it.
- `noUncheckedIndexedAccess` - `arr[i]` becomes `T | undefined`, forcing real null checking.
- `noEmit` - we run via tsx, compile only typechecks.
- `moduleResolution: "bundler"` - modern app-style resolution (allow `.ts` extensions in imports).

## 4. Layout convention (from the syllabus)

```
lld/
  src/            # classes, one per file
  tests/          # or colocated *.test.ts next to code - pick one and stay consistent
  notes.md        # trade-off log
```

Syllabus rule: one class per file, interfaces separated from implementations, tests next to code. For M0 a single colocated test file is fine.

## 5. The red-green drill

Create `lld/src/greeter.ts`:

```ts
export class Greeter {
  greet(name: string): string {
    // TODO: return "Hello, <name>!"
    return "";
  }
}
```

Create `lld/src/greeter.test.ts`:

```ts
import { describe, expect, it } from "vitest";
import { Greeter } from "./greeter";

describe("Greeter", () => {
  it("greets by name", () => {
    expect(new Greeter().greet("Ada")).toBe("Hello, Ada!");
  });
});
```

```bash
npx vitest run          # should be RED
```

Then make it pass:

```ts
return `Hello, ${name}!`;
```

```bash
npx vitest run          # GREEN
npx tsc --noEmit        # types clean
```

Add a second test for an edge case (empty name? whitespace? - pick one and defend it).

## 6. Wrap (the syllabus loop)

- Tests green
- One commit: `M0: workbench + red/green drill`
- One trade-off sentence for `lld/notes.md`: e.g. "chose tsx+vitest over ts-jest because zero build config and native ESM; cost is less jest pattern familiarity, fine since vitest API matches."
